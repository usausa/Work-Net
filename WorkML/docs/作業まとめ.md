# WorkML 実施内容まとめ

> 作成: 2026-06-20 / 更新: 2026-06-20 / 電力・電圧の保安機器ログによる予防保守を Azure × .NET で実現する検討・実装の記録。

## 1. 目的
複数拠点・**可変チャンネル**・**異なる基本電圧（100V/200V）** の保安機器ログから、予防保守（予測＋異常検知）を Azure の AI サービスと .NET で実現する。

## 2. 調査と意思決定
- 当初は「Azure の AutoML 系を .NET から叩く」想定だったが、調査で **Azure AI Anomaly Detector / Metrics Advisor が 2026/10/01 廃止**（新規作成も不可）と判明 → 専用の時系列異常検知サービスは採用不可。
- 代替を比較（**ML.NET** / **Azure ML AutoML** / **時系列基盤モデル**）。故障ラベル（履歴）が乏しい現場が多いため、**学習不要の基盤モデル**路線を選択。
- 基盤モデルを比較（TimeGEN-1 / TimesFM / Chronos-2 / Moirai / Lag-Llama）。**Azure ネイティブ（モデルカタログのサーバーレス API）で、予測と異常検知の両方が標準**の **TimeGEN-1**（Nixtla 製）を採用。

## 3. 設計の要点
- **異なる基本電圧 → 標幺値（p.u.）正規化**：実測値 ÷ 基本電圧。100V/200V を 1.0 中心の同一スケールに揃える。
- **可変チャンネル / マルチサイト → `unique_id`（1チャンネル = 1系列）**：`{Site}-{Device}-ch{n}`。Nixtla の long 形式 `unique_id, ds, y` に対応し、装置ごとにチャンネル数が違っても破綻しない。
- **データは 5分間隔**。サンプルは**装置ごとの CSV**で**長期間（1日288件 × 60 = 60日分 = 17,280件/チャンネル）**。
- .NET 連携は公式 SDK 無し → **HttpClient で REST**。エンドポイント / API キーはコード直書きせず**環境変数**で外出し。

## 4. 実装（構成）
- .NET **net10.0**（net9 は 2026/5/12 EOL のため）。
- ソリューションレイアウト（`WorkML.slnx` 直下に各プロジェクト）:
```
WorkML/
  WorkML.slnx
  WorkML/                アプリ（net10.0）
    Program.cs / Core/ / TimeGen/ / sample-data/
  WorkML.Tests/          xUnit テスト
  docs/                  設計・実装メモ・本書
```
- `sample-data/` は**装置ごと**の長期間 CSV（`dev01/02/03.csv`）＋生成スクリプト `generate-sample-data.ps1`。
- Azure 未接続でも「CSV 読込 → p.u. 正規化 → リクエスト JSON 生成」までローカル実行可能（実行で 103,680 点をロード）。

## 5. Azure 側の準備手順（README に記載済み）
1. Azure サブスクリプション（従量課金）。
2. Azure AI Foundry または Azure ML Studio のモデルカタログで `TimeGEN-1` を選択。
3. **サーバーレス API（Models-as-a-Service）** としてデプロイ（初回は Marketplace 規約同意）。
4. **エンドポイント URL と API キー**を取得し、環境変数 `TIMEGEN_ENDPOINT` / `TIMEGEN_APIKEY` に設定。

## 6. 主な学び
- クラウドの AI サービス・フレームワークは廃止が速い。**採用前に提供状況・サポート期限を最新情報で確認**する（net9 EOL も同様）。
- サードパーティ製でも Azure カタログ経由なら「Azure のサービス」として課金・認証・運用が統合される（Azure OpenAI と同じ構図）。
- 常時読み込まれるルール（規約）は盛りすぎると希釈する。**効果が明確なものに絞る**（ドキュメント作成ルールを 9→3 に圧縮）。

## 付録. 経緯メモ（解決済み）
作業中、開発環境のサンドボックス設定（`.claude/settings.local.json` の `sandbox.enabled: true`）により、ツールの書き込みが実ファイルシステムに反映されない不具合が頻発した。原因を特定して `false` に変更・再起動で解消。再起動でサンドボックス層の一部作業が失われたため、現存ファイルを実 FS 上で作り直して確定した。
